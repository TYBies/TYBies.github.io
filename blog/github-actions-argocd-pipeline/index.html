GitHub Actions and Argo CD: a CI/CD pipeline with clear responsibilities

Build one candidate. Review the deployment decision. Let GitOps reconcile it—and check what actually runs.

By Oluwatoyin Balogun · 4 November 2026 · Technical walkthrough

A green build is not a deployed application. A GitHub Actions and Argo CD CI/CD pipeline is easier to reason about when each system has one job: Actions produces and checks a release candidate; a reviewed Git change records the deployment decision; Argo CD reconciles that decision with Kubernetes.[2]

This is an illustrative walkthrough, not a claim of production execution. The local Docker Compose demonstration records a blocked failing candidate, promotion and a return to the previous version configuration. It does not demonstrate immutable-image rollback, GitHub Actions execution or Kubernetes deployment. Here, the next question is how those responsibilities would fit together.

1. Define the handoff before writing automation

Consider an application repository named orders-app and a deployment repository named orders-config. These are fictional names. The first owns source, tests and the Dockerfile. The second owns the manifests for staging and production. Argo CD recommends separating application source from deployment configuration.[2]

Assume the registry, cluster, Argo CD Application and repository access already exist. The Application must track the intended configuration branch and environment directory. Creating those foundations belongs to a separate bootstrap process; the Terraform bootstrap note explains why delivery automation cannot create every prerequisite for itself.

2. Build a candidate, not a moving target

For an approved application revision, run the agreed tests, build the container and exercise that built candidate. Publish it only after the required checks pass. Capture the registry digest of the published artifact and associate it with the source commit and test results. Do not silently rebuild a different image after testing and call it the same release.

A readable tag can help people find a build, but the deployment reference should identify the artifact precisely. Kubernetes supports registry/repository@sha256:…; the ellipsis here is explanatory, not a usable digest. Tags can move, while digests are immutable identifiers for image content.[4]

Keep the complete digest in the release record. Retain previously approved images in the registry, and ensure the cluster can pull them. Immutability does not guarantee availability, vulnerability safety or application correctness. A digest is a stable selection, not a substitute for testing.

3. Propose the deployment change with scoped access

Have a trusted promotion job open a pull request against orders-config. For example, change the named application container’s image field in environments/staging/deployment.yaml to the captured digest. Include the source commit, build result and previous image reference in the pull request. Review the rendered diff so an image update does not accidentally change a namespace, replica count or unrelated workload.

The workflow repository’s built-in GITHUB_TOKEN cannot simply write another repository. GitHub documents a GitHub App installation token for access beyond that boundary.[3] For this design, install a dedicated promotion app only on the configuration repository. Grant Contents write and Pull requests write for the proposed branch-and-PR operations, not repository administration. Preserve branch protections and required review rather than granting a bypass.

Protect the app’s private key as a secret, request an installation token scoped to the target repository and necessary permissions, and do not expose it to untrusted pull-request code. GitHub’s documented flow separates app registration, installation, credential storage and token creation.[3]

This Git credential is not AWS OIDC. If Actions needs AWS registry access, OIDC federation and the allowed AWS role are a separate connection.[6] Argo CD should use its own read-only Git access, not the promotion writer’s credentials.[7] The authentication-boundaries note covers those identities in detail.

4. Let Argo CD own reconciliation

Once the configuration pull request is merged, Argo CD detects the difference between the desired manifests and live resources. With automated sync enabled, CI does not need to call the Argo CD API to initiate deployment.[1] Avoid also running kubectl apply from the build job: that creates a second deployment writer outside this design’s Git handoff.

Choose automation policies deliberately. Automatic pruning, which removes resources no longer defined in Git, is not enabled by default. Self-healing of live drift is also a separate option; “auto-sync” does not mean every possible corrective action is enabled.[1] Review destructive changes and define who investigates failed reconciliation.

For production promotion, propose the same tested digest in the production configuration. Do not rebuild merely because the environment changed. Serialize or review competing promotion requests so an older build cannot overwrite a newer decision unnoticed.

5. Verify the revision, sync and application behavior

A merged pull request proves only that desired state changed. Check that Argo CD reports the intended configuration revision, a successful sync and healthy resources. Health is a separate assessment based on Kubernetes resource status, not proof that every user journey works.[8]

Confirm the expected image reference and ready replicas, then run a bounded smoke test through the application’s actual entry point. Define a timeout and an owner for failure. A successful build should not be presented as a successful rollout while these checks are pending.

Readiness probes determine whether a container can accept traffic; a failed readiness probe removes the Pod from matching Service endpoints.[5] They do not invent a meaningful readiness endpoint or validate business behavior. Configure them for the application, rather than treating “the process started” as sufficient.

6. Make the way back another reviewed change

With automated sync enabled, Argo CD’s direct history rollback is not available.[1] In this design, restore the previous approved image and compatible configuration through a new Git commit, commonly a reviewed revert of the promotion. Merge it, let Argo CD reconcile, and repeat the revision, health and smoke checks.

Review what the revert actually changes: later edits may depend on the release being undone. A direct cluster edit is not a durable rollback when Git still declares the newer version. Emergency procedures must explicitly account for reconciliation and restore a consistent source of truth.

Neither Git revert nor an older image undoes database writes or schema migrations. Establish backward compatibility, migration sequencing and data recovery separately. If the old application cannot use the new schema, an image rollback may make the incident worse. Agree that limitation before release, not during recovery.

Verification scope: official documentation and the existing local demo evidence informed this note. No executable workflow or manifest is provided or installed. No AWS deployment, GitHub Actions pipeline, Argo CD sync or immutable-image rollback was executed for this article.
