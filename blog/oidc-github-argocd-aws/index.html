OIDC, GitHub Actions and Argo CD: which system authenticates where?

One delivery pipeline, several trust boundaries. GitHub Actions, Git access, Kubernetes access and human login do not share one credential.

By Oluwatoyin Balogun · 2 November 2026 · Technical walkthrough

“Argo CD uses OIDC to authenticate to GitHub and AWS” sounds like a neat explanation. It combines several different connections, though. GitHub Actions can exchange a GitHub-issued identity token for AWS credentials. Argo CD reading a private GitHub repository is a separate operation, with separate credentials.[1][2]

The training infrastructure reviewed for this note contains an EKS module and an Argo CD Helm installation. That verifies the configuration’s intended platform, not a currently running cluster or its authentication settings. The flows below explain the boundaries; they are not a claim that every option was deployed in that project.

Start with the caller, not the cloud

Ask three questions for each connection: who is calling, which API receives the request, and what authorizes it? “It runs on AWS” does not answer those questions.

These paths are documented independently for a reason: success on one does not establish access on another.[1][2][9]

1. GitHub Actions proves which job is running

With id-token: write, a job can request a signed OIDC JSON Web Token from GitHub. That permission does not grant AWS access. The credentials action exchanges the token with AWS STS using AssumeRoleWithWebIdentity; AWS evaluates the configured identity provider and role trust before issuing temporary credentials.[1][6]

For the standard AWS audience, validate aud = sts.amazonaws.com. Restrict sub to the intended repository and branch or environment. Trust answers “who may assume this role?” The role’s permissions policy answers “what may that session do?” Keep permitted infrastructure or deployment actions narrow.[1]

This illustrative workflow shows only the authentication step. Replace the placeholder ARN with an approved role before use; no deployment step is included.

The action version is illustrative, not a latest-version claim; pin a reviewed full commit SHA in a production workflow. There is no checkout here because this example does not read repository files.

For repositories using the name-based subject format, a branch subject looks like repo:ORG/REPO:ref:refs/heads/main. Adding environment: production changes that to repo:ORG/REPO:environment:production; it is not the branch subject with another condition appended. Protect that environment’s allowed branches and approvals.[1]

Check the actual subject format. GitHub now documents immutable owner/repository IDs for newer or opted-in repositories. Do not assume the name-only example fits yours. Never “fix” a mismatch by trusting every repository or pull-request context. Untrusted pull-request code must not receive a privileged deployment role.[1]

2. Argo CD reads GitHub with Git credentials

Argo CD’s repo-server fetches repository content and renders manifests. It does not automatically inherit an Actions job’s OIDC token or AWS session. Private GitHub access supports GitHub App credentials, HTTPS tokens and SSH keys.[2][9]

For a team installation, prefer a GitHub App restricted to selected repositories with read-only Contents permission for manifest retrieval. The app authenticates to obtain an installation access token, which expires after one hour. Argo CD supports configuring the app identity and private key; that key still needs protected storage and rotation.[2][8]

A read-only SSH deploy key or narrowly scoped PAT can also work. Avoid personal, broadly privileged credentials as a convenient default. Keep repository secrets out of Git, restrict who can read their Kubernetes Secrets, and protect the branches Argo CD trusts: changing a manifest can change what gets deployed.[2][9]

3. Argo CD deploys through the Kubernetes API

When Argo CD manages its own cluster, the controller normally uses its Kubernetes service-account identity and the RBAC granted to it. It does not need AWS access keys simply to apply a Deployment or Service. Review the installed roles: broad defaults should not be mistaken for least privilege.[9]

External clusters need an explicitly configured connection, trusted TLS information, network reachability and credentials. For EKS, Argo CD documents awsAuthConfig with a cluster name and role ARN, using argocd-k8s-auth. Generic execProviderConfig is another credential mechanism; any referenced executable must exist in the Argo CD image.[3]

In the documented EKS-to-EKS pattern, Argo CD receives a management-role identity and assumes a target cluster role. IRSA uses the EKS cluster’s OIDC issuer and a Kubernetes service-account subject—not GitHub’s issuer or repository subject. EKS Pod Identity is a different setup, using its agent, associations and AWS service-principal trust. Choose the documented path supported by the actual deployment; do not combine the two configurations casually.[3]

An operator’s kubectl can likewise use aws eks get-token to obtain an IAM-authenticated EKS token. Authentication still needs authorization: EKS access entries associate IAM identities with access policies or Kubernetes groups governed by RBAC. An AWS role is not automatically Kubernetes administrator access.[5][7]

The distinction matters: creating an EKS cluster calls AWS APIs; creating a Kubernetes Service calls the Kubernetes API. Grant additional AWS permissions only for work that actually needs them. And Kubernetes on EC2 is not necessarily EKS—self-managed clusters require their own authentication design.

4. Human SSO is another boundary

Argo CD can authenticate people through a configured OIDC provider, directly or through Dex. A GitHub connector can support a GitHub-based login through Dex. Argo CD’s own RBAC then controls what that person can do in the UI or API. This login neither supplies the repo-server’s Git credential nor replaces the controller’s cluster identity.[4][9]

Trust still needs a starting point

The previous note on Terraform bootstrap ended with an identity dependency: a pipeline cannot assume a role that does not exist. A trusted administrator or approved bootstrap process must first establish the provider, role trust and permissions. OIDC removes stored long-lived AWS keys from that job, not this initial trust decision.[1][6]

When debugging, identify the failing boundary first: STS rejection, Git fetch, Kubernetes authorization or UI login. Changing all four credentials at once makes the system harder to understand.

Verification scope: the displayed YAML was parsed locally and its permission structure checked. Official documentation and read-only project configuration informed this note. No workflow was added, no AWS calls or live authentication tests were performed, and no cluster configuration was changed. Syntax checks do not prove that an IAM trust policy or deployment will work.

Keep the boundaries visible

Read the bootstrap note or explore the infrastructure training work. The useful question is not “does this use OIDC?” but “whose identity is trusted, by which system, for which action?”
