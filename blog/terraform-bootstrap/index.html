Terraform’s chicken-and-egg problem: bootstrapping remote state

Before Terraform can store state in S3, the bucket has to exist. The way out is a small, deliberate bootstrap boundary.

By Oluwatoyin Balogun · 2 November 2026 · Technical walkthrough

In my DataScientest bootcamp project, I worked on Terraform infrastructure and S3 remote state. That combination raises a useful question: if Terraform creates the infrastructure, what creates the place where Terraform keeps its state?

This is an illustrative pattern, not a reconstruction of that project’s deployment history. The examples below are newly written and intentionally separate the state foundation from the application. They do not establish how the training environment was deployed or locked.

The bucket cannot create itself first

With an S3 backend, terraform init initializes access to an existing bucket. Backend initialization happens before a resource plan or apply. Putting the bucket resource into the same root does not make Terraform create it before initialization.[1][2]

Nor can the backend use aws_s3_bucket.state.id: backend configuration cannot refer to resource attributes or input variables. A resource depends_on cannot reorder backend initialization.[3]

1. Create the foundation separately

Give bootstrap/ its own root configuration. Without a backend block, Terraform uses local state.[3] Keep this root small: the state bucket should outlive the application it supports.

Save this as bootstrap/main.tf. Supply a globally unique bucket name you control; the default region is Frankfurt. The AWS provider is pinned to the version used for this example’s validation, not presented as the latest release.

Before any deployment, an authorized operator must review the account, region, bucket name, permissions and costs, then initialize, plan and apply this root. Those cloud operations are not part of this article’s verification. Complete the protection resources before allowing workload writes.

2. Point the workload at that bucket

Save this separate configuration as workload/main.tf. It defines only the backend boundary; add your application resources and providers here, not the state bucket.

Native S3 locking arrived in Terraform 1.10; use_lockfile = true opts in. Current documentation deprecates DynamoDB-based locking, so it is not the default for this new example. Coordinate older clients before changing an existing team’s lock mechanism.[4][1]

Only after the bucket exists, initialize the workload with the same bucket name and region. This command contacts AWS; it was not run for this article:

The backend authenticates separately from the AWS provider. Provider settings do not automatically configure backend credentials or role assumption. Use an approved short-lived credential mechanism for each; never embed access keys in HCL or backend arguments.[1][3]

3. Keep the two states straight

Initializing workload/ does not migrate bootstrap/. The bootstrap state still owns the bucket and remains local. Restrict access, keep an encrypted backup outside the repository, and nominate an owner before treating it as a shared foundation.

Optionally move bootstrap itself to remote state later: back up its state, add an S3 backend in that same bootstrap root using a distinct key such as bootstrap/terraform.tfstate, then run terraform -chdir=bootstrap init -migrate-state. Review the migration prompts and verify the destination state and resource addresses before retiring the local copy. -reconfigure is not an equivalent migration flag: it prevents migration of existing state.[2][3]

  • Recovery: versioning helps recover older objects; it is not a tested recovery procedure. Retained versions and S3 requests also have costs.
  • Access: scope bucket listing and state reads/writes to the required paths. The lock object additionally needs read, write and delete permissions. Do not give routine workload automation bucket-administration rights.[1]
  • Protection: encryption and public-access blocking are a baseline, not a complete security policy. Review TLS enforcement and any KMS requirements. prevent_destroy is a Terraform guardrail, not an AWS deletion lock; removing its resource configuration removes that protection.[5]
  • Repository hygiene: exclude state, backups, saved plans, credentials and .terraform/. Plans can contain sensitive backend configuration. Commit the provider dependency lock file, .terraform.lock.hcl, instead.[3][2]

There is a second chicken-and-egg problem

A GitHub Actions job cannot assume an IAM role that does not yet exist. An already trusted operator identity must establish the OIDC provider and role—or reuse an approved existing provider—before the workload pipeline relies on them. Restrict trust to the intended repository and branch or environment, check the actual subject-claim format, and validate the audience. OIDC removes the need for long-lived GitHub AWS secrets, not the need for an initial trust decision.[6]

What was checked, without deploying

The two examples passed HCL parsing, terraform fmt -check and terraform validate using Terraform 1.10.5; bootstrap validation used the downloaded, HashiCorp-signed AWS provider 5.100.0. These are the tested versions, not an upgrade recommendation.

Checks ran with isolated credential discovery and backend initialization disabled. No AWS deployment, plan, apply or state migration was performed. Validation does not prove IAM access, bucket availability or recovery behavior.

My takeaway: bootstrap is not a shortcut around infrastructure as code. It is an explicit boundary for the resources and trust that ordinary automation needs before it can start.
